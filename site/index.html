Relay は 119・消防・警察・自治体などの公式な緊急通信手段を置き換えるものではありません。現在は開発段階であり、避難訓練・限定パイロット・技術検証向けです。画面上の「保存済み」「中継中」「受信済み」は、出動・受理・救助を保証しません。 Relay does not replace 119, fire departments, police, municipalities, or any official emergency communication channel. It is a development-stage project for drills, limited pilots, and technical validation. A UI state such as “saved,” “relaying,” or “received” does not guarantee dispatch, acknowledgement, or rescue.

大規模災害では、スマートフォンは動いていても、インターネットや携帯網は不安定になります。Relay は救助情報を端末内で暗号化し、そのとき使える経路 — Nearby・ローカル LAN・HTTPS Broker — を通じて、救助調整地点の PC Gateway へ運びます。 In a large-scale disaster a smartphone may still work while internet and cellular infrastructure becomes unstable. Relay encrypts rescue information on the device and moves it along whichever path is available — Nearby, local LAN, or an HTTPS Broker — toward a PC Gateway at the coordination point.

WHY RELAY

通信が「ある」と仮定しない設計Designed to not assume connectivity

Relay は、単一の通信経路に依存しません。使える経路を選び、届いた範囲を正直に表すことを優先します。 Relay does not depend on a single transport path. It prefers using whatever path exists and representing honestly how far a request has actually travelled.

⌁

ローカルファーストLocal-first

インターネット接続を前提にせず、Nearby や LAN を含む複数の経路を使います。端末が保存し、人が持ち運び、次の接点が転送する Store–Carry–Forward モデルです。 Instead of assuming internet connectivity, Relay uses multiple available paths including Nearby and LAN. A device stores information, a person carries it, and the next contact forwards it — the Store–Carry–Forward model.

⛨

暗号化された中継Encrypted relay

救助内容は Android 端末上で暗号化されます。中継する端末や Broker は、その内容を復号することを想定していません。 Rescue content is encrypted on the Android device. Intermediate relay devices and the Broker are not intended to decrypt it.

◎

正直な送達状態Honest delivery state

通信 API の成功を、救助地点への到達とは扱いません。目標は「成功したように見せること」ではなく、要請がどこまで進んだかをできる限り正確に表すことです。 A successful communication API call is not treated as proof of arrival at the coordination point. The goal is not to make communication look successful, but to show how far a request has really progressed.

HOW IT WORKS

暗号化された封筒を、使える経路で運ぶMove an encrypted envelope along whichever path exists

作成から受領までの流れは、経路が変わっても同じです。 The path from creation to receipt stays the same even when the transport changes.

  1. 01

    端末で作成Create

    救助要請または通常の安否・物資情報を、Android アプリで作成します。位置情報は明示的な同意があるときだけ更新されます。Create a rescue request or ordinary safety/supply information in the Android app. Location is updated only after explicit consent.

  2. 02

    端末内で暗号化Encrypt

    保存には Room + SQLCipher と Android Keystore を利用します。転送されるのは暗号化された Envelope です。Storage uses Room + SQLCipher with Android Keystore-backed protection. What travels is an encrypted Envelope.

  3. 03

    経路を選んで中継Relay

    Nearby による端末間の中継、ローカル LAN からの直接到達、HTTPS Broker 経由の一時保管を、利用可能なものに応じて使います。Use device-to-device Nearby relaying, direct local LAN delivery, or temporary HTTPS Broker storage depending on what is reachable.

  4. 04

    受領して署名Receipt

    PC Gateway は要請を保存し、Gateway 署名付きの Receipt を返します。担当者の受付・対応状況は別の署名済み状態として扱われます。The PC Gateway stores the request and returns a Gateway-signed Receipt. Staff handling state is tracked separately as its own signed state.

NEARBY

端末間の中継Device-to-device

近くの端末同士が差分を交換し、情報を持ち運びます。ACK は Peer ごとに管理し、切断時は冪等に再送します。Nearby devices exchange differences and carry information forward. ACKs are tracked per peer, and reconnection is handled idempotently.

LOCAL LAN

Gateway への直接到達Direct to Gateway

同じ LAN 上に Gateway があれば、そこへ直接届けます。Gateway は既定でループバックにのみバインドします。When a Gateway is reachable on the same LAN, Relay delivers directly. The Gateway binds to loopback by default.

HTTPS BROKER

一時的な中継地点Temporary relay

暗号化された Envelope・公開 Manifest・Receipt を一時的に中継します。重複排除、TTL、スコープ限定の資格情報を適用します。Temporarily relays encrypted Envelopes, public Manifests, and Receipts, applying deduplication, TTLs, and scoped credentials.

DELIVERY STATES

「送れた」と「届いた」は違う“Sent” is not the same as “received”

Relay は、通信 API の成功を救助地点への到達とは扱いません。状態は意図的に分けられています。 Relay does not treat a successful communication API call as proof that a rescue coordination point received a request. The states are intentionally distinct.

この端末に保存Saved on this device

ローカルに保存された段階です。まだ端末から出ていない可能性があります。Stored locally; it may not have left the device yet.

近くの端末で中継中Relaying through nearby devices

端末間を移動している段階です。救助地点からの確認はまだありません。In transit between devices; no rescue-point confirmation yet.

救助地点に保存Stored at the rescue point

PC Gateway の署名付き Receipt が検証された段階です。A signed Receipt from the PC Gateway has been verified.

受付・対応中・完了Accepted / In progress / Completed

Gateway 署名付きの職員対応状態が検証された段階です。A Gateway-signed staff handling state has been verified.

△

Nearby の転送完了、Peer の ACK、HTTP 2xx、Broker への保存、ブラウザ入力の完了だけでは、職員が要請を受理したことにも、救助活動が始まったことにもなりません。 Nearby transfer completion, a peer ACK, HTTP 2xx, Broker storage, or browser intake completion alone does not mean staff accepted the request or that rescue activity began.

SECURITY

境界ごとに、何を守るかを決めるEach boundary states what it protects

救助内容Rescue content

保存・転送の前に Android 上で暗号化します。中継端末と Broker は復号する想定ではありません。Encrypted on Android before storage or transfer. Relay devices and the Broker are not intended to decrypt it.

Gateway 登録Gateway enrollment

QR コードの読み取りだけでは不十分です。フィンガープリントの確認を必須とします。Scanning a QR code alone is insufficient; fingerprint confirmation is required.

PC Gateway の公開範囲PC Gateway exposure

既定ではループバックにのみバインドします。LAN への公開には明示的な操作が必要です。Binds to loopback by default. LAN exposure requires an explicit action.

Windows 上の秘密鍵Windows private keys

任意で DPAPI による保護を選べます。同じ Windows ユーザーと PC に秘密を結び付けます。Optional DPAPI protection can bind secrets to the same Windows user and PC.

訓練用入力口Drill intake

本番では無効化されます。同一生成元の確認、サイズ・形式・レート制限を検証します。Disabled in production. Validates same-origin behaviour, size, format, and rate limits.

公式情報Official information

信頼の基準点なしに真正性を主張せず、出所と検証状態を表示します。Shows provenance and verification state instead of claiming authenticity without a trust anchor.

i

Windows DPAPI は任意です。既定の「所有者のみ読み取り可能なローカルファイル」方式は、ハードウェアベースの HSM・TPM・KMS による鍵保護と同等ではありません。 Windows DPAPI is optional. The default owner-only local file model is not equivalent to hardware-backed HSM, TPM, or KMS key protection.

WHAT REMAINS

実運用の前に必要なことRequired before real-world operation

Relay が今もっとも必要としているのは、機能の追加よりも、実機・実ネットワーク・現実的な条件下での独立した検証です。 Relay benefits more from independent validation on physical devices, real networks, and realistic conditions than from simply adding more features.

  1. 実機と RF の検証Physical-device and RF validation

    複数の Android 端末、マルチホップの Nearby、BLE、再起動、Doze、省電力モード、バッテリー消費、熱挙動。Multiple Android devices, multi-hop Nearby, BLE, reboot behaviour, Doze, battery-saving modes, battery usage, thermal behaviour.

  2. 本番の信頼データProduction trust data

    Regional Root、署名済み Shelter Directory、Gateway 鍵、フィンガープリント検証手順。Regional Root, signed Shelter Directory data, Gateway keys, fingerprint-verification procedures.

  3. 本番インフラProduction infrastructure

    TLS、DNS、監視、バックアップ、Broker の高可用性、RTO/RPO 目標、障害訓練。TLS, DNS, monitoring, backups, Broker HA, RTO/RPO targets, failure drills.

  4. 運用とプライバシーOperations and privacy

    保存期間、削除、同意、責任範囲、職員研修、法務レビュー、保険、通信規制の確認。Retention, deletion, consent, responsibility boundaries, staff training, legal review, insurance, communications-regulation review.

  5. 本番配布Production distribution

    組織による Android 署名、Windows Authenticode、リリース承認、代表端末へのインストール検証。Organizational Android signing, Windows Authenticode, release approval, installation validation on representative devices.

GET INVOLVED

いちばん役に立つ貢献は、検証ですThe most useful contribution is validation

複数端末での Nearby / LAN 配送の再現、端末ベンダーや Android バージョン、省電力設定による挙動の報告、避難訓練の視点からの UI/UX レビュー、PC Gateway の運用手順や鍵管理・障害処理・保存期間のレビューなどを歓迎します。 Reproducing Nearby / LAN delivery across multiple devices, reporting behaviour across vendors, Android versions and battery-saving configurations, reviewing UI/UX from a drill perspective, and reviewing Gateway setup, key management, failure handling and retention are all especially useful.
